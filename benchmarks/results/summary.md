# rowback benchmark summary

Generated by `benchmarks/summarize.py` from the raw JSON files in this directory. Every number below comes from those files.

## How to read these numbers

- Everything runs on one 8 GB Apple M2 laptop: the source PostgreSQL, the history PostgreSQL, pgbench (all three inside one 4 vCPU Docker VM) and the capture daemon (on the host). They compete for the same CPU cores and the same disk, so the overhead figures below are inflated relative to a deployment where the daemon and history database run on separate machines. Treat them as an upper bound for this hardware.
- Unthrottled, median TPS fell by 29% to 44% with capture on. Per-run TPS varies widely within a configuration (see the per-run line), so the ordering between REPLICA IDENTITY DEFAULT and FULL most likely reflects contention noise; it should not be read as FULL being cheaper.
- At a fixed 5,000 TPS every configuration sustained the target rate, but median p99 latency rose from about 4 ms without capture to 69 to 291 ms with capture, again with large run-to-run spread. The tail comes from CPU contention on the shared machine.
- The fixed-rate capture_default row uses 2 of 3 runs: the missing run hit a capture daemon crash (libpq dropped the replication stream with a bare DatabaseError that the daemon did not treat as a connection error). That bug is fixed and covered by tests; the run was not repeated.
- History storage measured 519 to 671 MB per million captured row changes (compressed row images plus indexes), highest with the context trigger on.
- In every overhead run the number of captured row changes equals the number committed, so no change was lost.

## Recovering from a bad DELETE: rowback undo vs restore

Source: `results/undo_vs_restore.json`, `results/undo_vs_restore_5m.json` (one dataset size per file, each from a separate run of `benchmarks/undo_vs_restore.py` on the same machine)

- Host: Apple M2, 8 GiB RAM, macOS-26.5.1-arm64-arm-64bit
- Docker VM (colima): 4 vCPU, 3.8 GiB; PostgreSQL 17.11 (Debian 17.11-1.pgdg13+2) (postgres:17), fsync on, synchronous_commit on, shared_buffers 512MB
- Capture daemon runs on the host (Python 3.12.9); history database is a separate PostgreSQL container on the same VM
- Each dataset: orders table (bigserial PK + secondary index) seeded with N rows, tracked with REPLICA IDENTITY FULL and the context trigger, capture daemon running. A pg_dump -Fc and a pg_basebackup (WAL archiving on) are taken, then 1,000 ordinary writes. Each incident deletes K rows chosen at random in one statement, then 500 inserts and up to 500 updates of other rows happen before the undo.
- rowback undo time = timeline search + plan (load and decompress history) + apply (one transaction), measured in-process. Correctness is checked with an md5 over the victim rows before and after, and by checking every later good write survived.
- pg_restore = `pg_restore -j 4` of the dump into a fresh database. PITR = copy the base backup + replay archived WAL to just before the last incident + promote, measured until the server accepts writes. Neither baseline includes the time to notice, provision or repoint applications, so both are lower bounds.

Each row is a single run, not a median, so treat the timings as one sample on a shared laptop. The first 5,000,000-row attempt (`results/undo_log.txt`) ran out of space in the 20 GiB Docker VM disk because the benchmark helpers had been leaking anonymous container volumes across earlier runs. After the helpers were fixed and the leaked volumes removed, the 5M dataset was rerun in full (`results/undo_log_5m.txt`). In the failed attempt the 10,000-row incident undid in 3.82 s against 2.13 s in the rerun, which gives a sense of run-to-run spread.
